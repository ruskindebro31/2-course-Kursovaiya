# ФУНКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ
## Candels Project - Интернет-магазин свечей ручной работы (Траектория В)

## 1. ТРЕБОВАНИЯ К СИСТЕМЕ В ЦЕЛОМ

### 1.1 Общие требования
Система должна предоставлять пользователям возможность:
- Просматривать каталог свечей ручной работы
- Регистрироваться и аутентифицироваться как покупатели или мастера
- Покупать свечи и оставлять отзывы
- Заказывать персонализированные свечи
- Получать персонализированные рекомендации
- Получать real-time уведомления о заказах и отзывах

### 1.2 Нефункциональные требования
- Время отклика системы не более 2 секунд
- Поддержка одновременной работы 500+ пользователей
- Время доступности системы 99.9%
- Защита от CSRF, XSS, SQL-инъекций
- Безопасная обработка платежной информации

## 2. ТРЕБОВАНИЯ К УПРАВЛЕНИЮ ПОЛЬЗОВАТЕЛЯМИ

### 2.1 Регистрация
**FR-1.1**: Система должна позволять новым пользователям регистрироваться с выбором роли (покупатель или мастер).
**FR-1.2**: Система должна отправлять подтверждающее письмо на email пользователя после регистрации.
**FR-1.3**: Система должна проверять уникальность email и username.
**FR-1.4**: Система должна требовать подтверждения email для активации учетной записи.

### 2.2 Аутентификация
**FR-2.1**: Система должна предоставлять форму входа с email и паролем.
**FR-2.2**: Система должна использовать JWT-токены для аутентификации.
**FR-2.3**: Система должна предоставлять access и refresh токены.
**FR-2.4**: Система должна автоматически обновлять токены при необходимости.

### 2.3 Управление профилем
**FR-3.1**: Пользователь должен иметь возможность редактировать свой профиль.
**FR-3.2**: Пользователь должен иметь возможность загружать аватар.
**FR-3.3**: Пользователь должен иметь возможность настраивать адреса доставки и оплаты.
**FR-3.4**: Мастера должны иметь возможность заполнять портфолио и специализацию.
**FR-3.5**: Пользователь должен иметь возможность управлять предпочтениями контента.

## 3. ТРЕБОВАНИЯ К УПРАВЛЕНИЮ ПРОДУКТАМИ

### 3.1 Просмотр каталога
**FR-4.1**: Система должна отображать каталог свечей с фильтрацией и поиском.
**FR-4.2**: Система должна позволять фильтровать свечи по категориям, цене, ароматам, цветам.
**FR-4.3**: Система должна позволять искать свечи по ключевым словам.
**FR-4.4**: Система должна отображать детальную страницу свечи с описанием и фотографиями.

### 3.2 Управление свечами мастером
**FR-5.1**: Авторизованные мастера должны иметь возможность добавлять свечи.
**FR-5.2**: Мастера должны иметь возможность редактировать свои свечи.
**FR-5.3**: Мастера должны иметь возможность загружать фотографии к свечам.
**FR-5.4**: Мастера должны иметь возможность указывать параметры свечей (ароматы, цвета, размеры).
**FR-5.5**: Мастера должны иметь возможность управлять количеством в наличии.

### 3.3 Категории и теги
**FR-6.1**: Система должна предоставлять список доступных категорий.
**FR-6.2**: Администраторы должны иметь возможность создавать и редактировать категории.
**FR-6.3**: Свечи должны быть привязаны к одной или нескольким категориям.

## 4. ТРЕБОВАНИЯ К СИСТЕМЕ ЗАКАЗОВ

### 4.1 Корзина покупок
**FR-7.1**: Пользователи должны иметь возможность добавлять свечи в корзину.
**FR-7.2**: Система должна моментально обновлять содержимое корзины (оптимистичное обновление).
**FR-7.3**: Пользователи должны иметь возможность изменять количество товаров в корзине.
**FR-7.4**: Пользователи должны иметь возможность удалять товары из корзины.

### 4.2 Оформление заказа
**FR-8.1**: Пользователи должны иметь возможность оформлять заказы из корзины.
**FR-8.2**: Система должна позволять указывать адрес доставки и способ оплаты.
**FR-8.3**: Система должна моментально подтверждать заказ (оптимистичное обновление).
**FR-8.4**: Пользователи должны получать подтверждение заказа по email.

### 4.3 Отслеживание заказов
**FR-9.1**: Пользователи должны иметь возможность отслеживать статус своих заказов.
**FR-9.2**: Система должна отправлять уведомления об изменении статуса заказа.
**FR-9.3**: Мастера должны видеть заказы своих изделий.
**FR-9.4**: Система должна позволять отменять заказы в определенные сроки.

## 5. ТРЕБОВАНИЯ К СИСТЕМЕ ОТЗЫВОВ

### 5.1 Оставление отзывов
**FR-10.1**: Покупатели должны иметь возможность оставлять отзывы на купленные свечи.
**FR-10.2**: Система должна моментально отображать новые отзывы (оптимистичное обновление).
**FR-10.3**: Пользователи должны иметь возможность оценивать свечи по 5-балльной шкале.
**FR-10.4**: Отзывы должны содержать текстовое описание.

### 5.2 Управление отзывами
**FR-11.1**: Мастера должны иметь возможность просматривать отзывы на свои свечи.
**FR-11.2**: Администраторы должны иметь возможность модерировать отзывы.
**FR-11.3**: Пользователи должны иметь возможность редактировать свои отзывы.
**FR-11.4**: Система должна показывать средний рейтинг свечи.

## 6. ТРЕБОВАНИЯ К ПЕРСОНАЛИЗАЦИИ

### 6.1 Персонализированные заказы
**FR-12.1**: Пользователи должны иметь возможность заказывать персонализированные свечи.
**FR-12.2**: Система должна позволять выбирать параметры персонализации (ароматы, цвета).
**FR-12.3**: Система должна показывать предварительный просмотр персонализации.
**FR-12.4**: Система должна позволять обсуждать детали с мастером через чат.

### 6.2 Чат с мастером
**FR-13.1**: Пользователи должны иметь возможность общаться с мастерами в реальном времени.
**FR-13.2**: Система должна поддерживать WebSocket-чаты.
**FR-13.3**: Сообщения должны сохраняться в истории чата.
**FR-13.4**: Система должна уведомлять о новых сообщениях.

## 7. ТРЕБОВАНИЯ К СИСТЕМЕ УВЕДОМЛЕНИЙ

### 7.1 Real-time уведомления
**FR-14.1**: Система должна отправлять уведомления через WebSocket в реальном времени.
**FR-14.2**: Мастера должны получать уведомления о новых заказах их изделий.
**FR-14.3**: Пользователи должны получать уведомления о новых отзывах.
**FR-14.4**: Система должна отправлять уведомления об изменении статуса заказа.

### 7.2 Управление уведомлениями
**FR-15.1**: Пользователи должны иметь возможность отмечать уведомления как прочитанные.
**FR-15.2**: Пользователи должны иметь возможность настраивать типы уведомлений.
**FR-15.3**: Система должна позволять удалять уведомления.
**FR-15.4**: Система должна группировать уведомления по типам.

## 8. ТРЕБОВАНИЯ К АДМИНИСТРАТИВНОЙ ЧАСТИ

### 8.1 Управление пользователями
**FR-16.1**: Администраторы должны иметь возможность просматривать список пользователей.
**FR-16.2**: Администраторы должны иметь возможность блокировать/разблокировать пользователей.
**FR-16.3**: Администраторы должны иметь возможность назначать роли пользователям.
**FR-16.4**: Администраторы должны иметь возможность подтверждать статус мастеров.

### 8.2 Управление контентом
**FR-17.1**: Администраторы должны иметь возможность модерировать свечи.
**FR-17.2**: Администраторы должны иметь возможность удалять свечи.
**FR-17.3**: Администраторы должны иметь возможность удалять отзывы.
**FR-17.4**: Администраторы должны иметь возможность управлять категориями.

### 8.3 Статистика и отчеты
**FR-18.1**: Администраторы должны иметь доступ к статистике системы.
**FR-18.2**: Система должна предоставлять отчеты по продажам.
**FR-18.3**: Система должна отображать метрики популярности свечей.
**FR-18.4**: Система должна показывать активность мастеров.

## 9. ТРЕБОВАНИЯ К ИНТЕРФЕЙСУ ПОЛЬЗОВАТЕЛЯ

### 9.1 Адаптивный дизайн
**FR-19.1**: Интерфейс должен корректно отображаться на различных устройствах.
**FR-19.2**: Система должна поддерживать мобильные устройства.
**FR-19.3**: Интерфейс должен быть интуитивно понятным для e-commerce.

### 9.2 Реактивность
**FR-20.1**: Интерфейс должен моментально реагировать на действия пользователя.
**FR-20.2**: Система должна использовать оптимистичные обновления.
**FR-20.3**: Система должна показывать индикаторы загрузки.
**FR-20.4**: Система должна поддерживать ленивую загрузку изображений.

## 10. ТРЕБОВАНИЯ К БЕЗОПАСНОСТИ

### 10.1 Защита данных
**FR-21.1**: Система должна шифровать пароли пользователей.
**FR-21.2**: Система должна использовать HTTPS для всех соединений.
**FR-21.3**: Система должна защищать от CSRF-атак.
**FR-21.4**: Система должна безопасно обрабатывать платежную информацию.

### 10.2 Управление сессиями
**FR-22.1**: Система должна автоматически завершать сессии после истечения срока действия токенов.
**FR-22.2**: Пользователи должны иметь возможность выйти из системы.
**FR-22.3**: Система должна отслеживать активные сессии.

## 11. ТРЕБОВАНИЯ К ПРОИЗВОДИТЕЛЬНОСТИ

### 11.1 Кэширование
**FR-23.1**: Система должна кэшировать часто запрашиваемые данные (каталог, категории).
**FR-23.2**: Система должна использовать клиентское кэширование (React Query).
**FR-23.3**: Система должна инвалидировать кэш при обновлении данных.

### 11.2 Оптимизация
**FR-24.1**: Система должна использовать пагинацию для больших каталогов.
**FR-24.2**: Система должна лениво загружать компоненты.
**FR-24.3**: Система должна минимизировать количество HTTP-запросов.
**FR-24.4**: Система должна оптимизировать изображения.

## 12. ТРЕБОВАНИЯ К ИНТЕГРАЦИИ

### 12.1 API
**FR-25.1**: Система должна предоставлять RESTful API для всех операций.
**FR-25.2**: API должен поддерживать JWT-аутентификацию.
**FR-25.3**: API должен возвращать данные в формате JSON.
**FR-25.4**: API должен поддерживать фильтрацию и сортировку.

### 12.2 WebSocket
**FR-26.1**: Система должна поддерживать WebSocket-соединения.
**FR-26.2**: WebSocket должен использоваться для real-time уведомлений и чата.
**FR-26.3**: Система должна корректно обрабатывать разрывы WebSocket-соединений.

## 13. ТРЕБОВАНИЯ К ТЕСТИРОВАНИЮ

### 13.1 Unit-тесты
**FR-27.1**: Backend должен иметь покрытие unit-тестами не менее 80%.
**FR-27.2**: Frontend должен иметь покрытие unit-тестами не менее 70%.

### 13.2 Интеграционные тесты
**FR-28.1**: Система должна проходить интеграционное тестирование.
**FR-28.2**: Должны тестироваться все основные пользовательские сценарии.
**FR-28.3**: Должны тестироваться сценарии персонализированных заказов.
**FR-28.4**: Должны тестироваться сценарии реального времени.

Эти функциональные требования полностью соответствуют траектории В для интернет-магазина свечей ручной работы и обеспечивают реализацию всех необходимых возможностей e-commerce платформы с продвинутой клиентской логикой, WebSocket-уведомлениями и системой оптимистичных обновлений.
